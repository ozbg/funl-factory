Factory Field Guide

How an idea becomes a built, tested app, and how it keeps getting better: who does what at each stage, what moves a card, what "done" means, and which skill to reach for.

The path

Six steps. The first five build the first version; the sixth keeps it improving, for as long as the app lives. You sign a few things; agents do the legwork and ask only when they must.

The chain, in order. Each step ends by naming the next one.

  1. /north-star: drills each must-have to the clarity bar → clarity review (a fresh Fable agent) → you sign the postcard.
  2. /mockup: tweak rounds → outside review (a fresh Fable agent) → design polish (frontend-design) → postcard check → north-star amendment if a must-have changed.
  3. /super-board onboard: sets up the board. Skipped if the app already has a board.
  4. /to-board --dry-run: spec → spec review (a fresh Fable agent) → cards → blind review and Haiku read → your scope review. Nothing filed.
  5. /to-board: files the cards to Ready.
  6. You sign zones.yaml → /super-board lint → /super-board run. The run ends with an agent walking every screen of the real app → report.
  7. From then on, iterate: the feedback icon and /super-collect feed agent triage. Bugs and tweaks go straight to Ready and the next run; a body of work goes back through grilling and a brief you sign, then /to-board.

Run Define (/north-star, /mockup, /to-board) in the app's folder, or in an empty folder to test an idea. /to-board --dry-run writes the spec and shows the cards without touching a board.

Step by step

What each step does, what you do, what it produces, and how it feeds the next. Run every step in the same app folder: each one finds the last one's files by itself.

1

/north-star · the vision

you answer
Does
A short interview. It listens first, then offers one-line guesses you accept or fix. It pins down why the app exists, the few things it must do, what it must never do, the one thing users do most (the core loop), and one small moment of delight. Then it drills each must-have to a clarity bar: who uses it and what triggers it, what a good result looks like, what you'll actually ask or do on day one and what a good answer is, and the one edge case that would change the design. It drills the weakest must-have first, one question at a time with a guess you can accept, gives a clear one a single confirming question, and after each answer shows which must-haves are clear and which it's still drilling. When they're all clear, or you say "enough", a fresh Fable agent reads only the draft and your own words and hands back up to 6 questions a builder or the AI would otherwise guess, including any business rule the build will need (when a client counts as won, who sees what, money, deletion), each with a suggested answer; the factory asks the ones it agrees with, in the same drill. Those day-one questions later become the AI's exam and the agent walk's script. It reads back a postcard: two or three sentences describing a good day with the app. Then a fresh agent sketches the app from the postcard alone, and you score how close it is.
You
Answer until every must-have is clear: about 12 questions is typical, not a cap. Say "enough" any time; you still get the review's questions once, as one list you can answer in a single reply or skip, and whatever is still unclear is written down as assumed. Then say yes, nearly or no to the postcard, and score the sketch 1–5. Re-read it the next morning.
Output
A one-page vision, not a spec: docs/shape/north-star.md. It has the postcard, the north-star outcome, the core loop, numbered must-haves, must-nevers, the sparkle, nice-laters and what was assumed. No screens, fields or tech. Details you mentioned go to docs/shape/later.md; the run is logged in docs/shape/north-star-log.jsonl.
Next
Run /mockup in the same folder. It reads north-star.md itself; you pass nothing.
2

/mockup · the feel

you click
Does
Builds 2–3 radically different mock-ups of the core loop, all in one web page with fake but realistic data: one tab per step of the loop, a switch at the bottom to flip between versions, buttons that really do something. The sparkle is shown working, and every must-never visibly doesn't happen.
Then
Once you say it feels right: a fresh Fable agent that never saw the chat reviews it against the north star and your own words (kept in docs/shape/mockup-log.md) and returns at most 8 ranked issues. The factory gives its take on each; you decide. Then a design polish with frontend-design fixes sizing, spacing and type, keeping every screen and button; you see before and after at desktop and phone width and keep what you like.
You
Click through each version, pick one, ask for at most two rounds of tweaks, say which review findings to take and which polish to keep, then answer "Is that the postcard?" If a must-have turns out wrong, it sends you back to /north-star.
Output
A clickable mock-up: docs/shape/mockup.html, one file that opens with a double-click in any browser, your pick showing first. Each screen has a fixed name (#screen-capture) that the build cards link to, so builders copy the look. It adds a Mock-up: … · postcard: yes line to north-star.md; small tweaks go to later.md; your inputs and the factory's pushbacks go to mockup-log.md. The mock-up is the design truth until the first build ships. Then it's frozen, and screenshots of the real app become the baseline that later changes are checked against.
Next
No board yet: /super-board onboard, which then names /to-board --dry-run. A board already: /to-board --dry-run in the same folder. It reads the north star and the mock-up itself.
3

/to-board · the plan and the cards

factory decides
Does
  1. Reads the north star, the mock-up and any existing code, then makes the technical calls: stack, data model, how it's tested.
  2. Writes the one-page build spec.
  3. Spec review: a fresh Fable agent checks the spec against the north star, the mock-up and your inputs, then reads it as an attacker: can one client reach another's data, what works without signing in, which path breaks a must-never. It also runs a capability pass: can this design answer each day-one question? Any rule the north star never asked for is flagged, for you to keep or drop, so the spec can't quietly cripple the app. It also flags mock-up screens the spec doesn't support and anything a builder or the AI would have to guess. A finding that needs your business call is one the north star missed, and the retro counts it. The factory gives its take on each finding; you decide what changes.
  4. Drafts the zone map: which files are risky (red), features (amber) or looks only (green).
  5. Cuts the work into cards: a foundation card first (the skeleton and one finished example of each pattern), a thin slice for each step of the core loop, and a Demo card last that walks the whole loop. Every screen card carries its mock-up section: the anchor, the markup and the style classes to use, and a check that the screen matches. Any mock-up feature a card leaves out is listed on the card. Every AI feature gets an exam card: its day-one questions with expected answers, run on the real model.
  6. Blind review: a fresh agent checks the cards against the north star without seeing the spec, and Haiku reads every card with what a builder gets (the whole spec and the files the card lists) and lists any question where a wrong guess would fail a check. One round of fixes.
  7. Shows you the card table with the verdict.
  8. Commits and pushes its files, so builders can see them, then files the cards to the board and writes the coverage map.
You
Decide on the review findings. Then look at the table once and say what's missing or unwanted, including any mock-up feature that was cut. That's scope only; how it's cut is the factory's call. Then sign the zone map.
Output
docs/shape/spec.md: the build spec (postcard on top, must-haves, must-nevers as numbered rules I1, I2…, volumes, tech decisions, data model, the data shapes where cards meet, the test command).
docs/agents/zones.yaml: the draft zone map, for you to sign.
docs/shape/coverage.md: which cards deliver each must-have, the mock-up features cut, the exam cards and the Demo card.
The cards themselves, in the board's Ready column on GitHub.
Next
Sign zones.yaml, then /super-board lint. The files are already committed: builders work from main and only see what's there, so run /to-board on main. Try it first with /to-board --dry-run: it writes the spec and shows the table but files nothing.
4

/super-board run · the build

factory
Does
Drains the board in waves. Before each wave the planner picks the cards: it refuses a card with no Files: line or no checkboxes, and holds back one whose test the runner never runs or whose blocker isn't on the board. For each card: a builder (Haiku, or Sonnet for red and flagged cards) works in its own copy of the code, writes the tests first, makes the change and opens a draft PR. QA proves every check, and for a screen it puts a screenshot of the app beside the mock-up and lists every difference; an unaccepted difference sends the card back. A Sonnet reviewer reads it (Opus on red cards, after two read-only agents truth-check the PR), and the merge gate re-runs everything against the latest main before merging. Cards that don't pass go back, at most 1–3 times by zone, then wait in Blocked with the reason. Waves run 3 cards wide by default (up to 6 when you ask), picked so no two cards touch the same files. After each wave the foreman reconciles: it closes merged issues, writes one line per card to the run log, scores the wave and checks health (see Getting better).
You
Nothing, unless a digest asks: a 🙋 card (money, auth, a destructive schema change, a live database) or a budget question. If a safety check refuses a lane's merge, the foreman runs the merge gate itself, pinned to the exact commit that was reviewed. You aren't asked to click merge on work you'd just approve anyway.
Output
Merged PRs on main, cards in Done, a short digest on each merge, breach or question. /super-board status shows where it is any time.
Then
The agent walk. When the Demo card is Done, a Sonnet agent uses the real app as you would: every screen, with the real AI settings. It works from a written checklist and the day-one questions, takes a screenshot of each screen and compares it with the mock-up, and runs every AI exam. The screenshots and findings go in docs/super-board/runs/<date>-walk/. Whatever fails is filed as feedback, so it goes through step 6, and you get one question: build the fixes now, or accept them for later. The milestone isn't done until the walk passes or you accept its findings.
Next
/super-board report, then use the app yourself and check it against the postcard.
5

/super-board report · the score

you read
Does
Puts the whole app on one page: how long Define took, days to build, cost against budget, how many cards passed first time, rework, rounds, whether the demo passed, and the postcard. It also scores the product, not just the build: how many screens match the mock-up, the AI exam scores, the agent walk's pass rate, and how many mock-up features were cut. Each against a target, with up to three things to change next time.
Output
Printed in the chat. With --log, one line in docs/super-board/factory-log.jsonl; --compare lists every app side by side. The retro beside the run log covers product quality as well as process, and every change the factory itself needs becomes a ticket on the factory repo (see Getting better).
Next
The app is in use. Every change from here goes through step 6.
6

Iterate · bugs, tweaks and bigger work

you click and type
Does
Every app the factory builds has a small feedback icon. Click it and type a line. It captures the screen, the page, the app's state and recent logs, and you can mark up the screenshot if words aren't enough. The item is saved inside the app; nothing is sent anywhere. /super-collect then picks it up with the agent walk's findings and real errors. It removes contact details, merges repeats and checks each one. An agent triages each item into one of three tracks (see Iterating). It either fixes it, a card in Ready (the item breaks a spec line, rule or mock-up screen it can point to), or proposes it to you, a card in Backlog with its recommendation (anything new, anything that changes direction, anything it's unsure about).
You
Click and type when something's wrong or could be better. Read the proposals digest: accept each one, or reject it with a one-line reason. A rejected item is closed and never filed again. Sign the brief for a body of work.
Output
Bug and tweak cards in Ready for the next run. A proposals digest with a recommendation on each. For a body of work: a signed brief and an updated spec, then new cards from /to-board.
Next
/super-board run picks up the new cards. Every run ends with an agent walk and a report, the same as the first build.

Rescope · a body of work

/north-star again, then /to-board

  • Grill the change and write its exam, then sign the brief and re-sign the postcard if it moved
  • /to-board updates the spec, files only new cards, and lists the ones to drop for you to close

Iterating

After the first build, every change takes one of three tracks. What it touches picks the track, not what it's called: anything that touches a rule (I1…), the data model or more than one screen is a body of work.

TrackWhat it isWhat it goes throughYou
BugThe app differs from the spec, a rule or the design baselineTriage reproduces it and writes a card with a test that fails now. Then build, QA and review, like any card.Nothing: the spec already decided what's right
TweakA look, copy or behaviour change on one screen, with no contract or data changeA card with before and after. QA's proof is the new screen beside the baseline, and the baseline updates on merge.Only if it changes how the product behaves
Body of workAnything that touches a rule, the data model or more than one screen, or is newa. Grill it, including day-one questions
b. Write the exam: questions and expected answers
c. Write the brief: what, why, rules it changes, out of scope
d. A fresh Fable agent reviews the brief
e. You sign it
f. The spec is updated, then /to-board cuts cards
g. The run, the agent walk, the exam on the real model, the report		Accept the proposal; sign the brief

Fix or propose. Triage fixes on its own only when the item points to the spec line, rule or baseline screen it breaks, touches one screen, changes no contract or data model, and isn't red zone. Everything else is proposed, and so is anything triage is unsure of. Auto-fix cards per run are capped (5 by default), and the rest wait in your digest, so a noisy week can't take over the board.

The brief. A body of work's brief lives in docs/shape/briefs/, one page with a Signed: line like the north star. Its cards name it, and lint keeps them out of Ready until you've signed it.

Nothing leaves the app. The feedback icon saves to the app's own data folder, so an app that promises no outbound calls keeps that promise. Redaction happens on the factory side, before anything reaches GitHub. Screenshots never leave your machine: the card says in words what the screenshot shows.

Where security happens

In layers, from every session down to the merge. Sized for small business apps: tight where data can be lost or leaked, light elsewhere.

WhereWhat protects you
Every sessionGuard hooks block reading secrets (.env, keys, credentials), writing a live API key into a file, deleting anything outside the project, and work outside the project's worktree folder. Agents check a key exists by name only, never its value.
/north-starYou name the must-nevers: lose data, leak it, send without asking, show it to the wrong person.
/to-boardEach must-never becomes a numbered rule (I1…) with a test. Files that could break one go in the red zone of zones.yaml, which you sign.
BuildRed cards run on Sonnet and write a test for each rule they touch first. Auth, billing, upgrades and third-party APIs: the builder reads the official docs before writing code.
QAOn red and boundary amber cards, /pr-security-review checks the diff for injection, auth bypass, secrets, code execution and data exposure. A finding fails the card. Red cards also get one deliberate break per guarded line, to prove the test catches it.
ReviewRed cards get an adversarial check before review: two checkers try to prove the code wrong, and the reviewer weighs their score. A red card whose check did not run is blocked, never merged.
MergeMoney, auth and destructive schema changes (drop, truncate, rename) wait for you. Additive migrations run only on databases you allowed. A live database is always yours.

Not covered: a whole-system penetration test. The security pass reads each change, not the whole repo.

Code standards

No written style guide, on purpose. The models already name things well and keep functions short, and a rule only a person can judge becomes a reason to bounce cards. So the standard is what a tool checks, plus a few rules aimed at how parallel AI builders actually go wrong: different names for the same thing, and building too much.

Test firstEvery acceptance check gets a test that fails before the change and passes after.Builder (/tdd), QA, merge gate
Smallest safe changeOnly the files the card lists. Copy the pattern the foundation card set; don't invent a new one.Review: scope drift

The reviewer sorts every finding as a Gap (something asked for is missing), a Bug, a Verification miss (the proof doesn't prove it), Scope drift, or Over-engineering. Only a finding that cites a check, a rule, a zone bar line or a reproducible bug can send a card back.

Getting better

The factory reviews itself at three speeds: after every wave, at the end of every milestone, and between runs. Every lesson ends up as a change to a file: a card, a config value or a factory ticket. A lesson that only lives in the chat is lost at the next run.

StepWhat happens

Owner-found defectsAnything you find in the first days of use that the walk passed is a gap in the walk's checklist. It goes in the retro, and the checklist fix becomes a factory ticket.

Between runs: the factory loop

Spot
A lane result shows a factory problem (a script that blocks, a wrong path, a model that keeps bouncing), the retro lists one, or you ask for a change. It becomes a factory ticket in the same turn, not a note in the chat.
Ticket
On ozbg/funl-factory-master, label factory, one ticket per change, in the same card format as the apps. Factory work never goes on an app's board.
Build
A branch in the factory repo, a PR to main, and the pack's own safety tests green. Small changes the foreman makes itself; bigger ones go to an agent that works only in the factory repo.
Review
The foreman reviews every factory PR. You approve any change to decision rights, privacy rules, merge policy, the money, auth or destructive-schema gates, or spend limits.
Roll out
Between runs, never mid-run: the install line in each app, landed through the app's own PR as 🔧 [chore] factory: upgrade to <sha>. The next run starts on the better factory.
Mid-run
When a factory bug blocks a run, the foreman fixes the app's installed copy so the run continues, tickets it in the same turn and sends the fix upstream. The ticket closes only when the fix is merged in the factory repo, because the next upgrade would otherwise overwrite it.

Optional: with calibration.enabled, a completed run with every card merged and proven hands a short receipt of what happened to an installed learning skill, which may edit the skill files you named. It's off by default and never runs on a halted or partial run.

Built on spec-driven development

The factory follows the same principles as current spec-driven tools such as OpenSpec and GitHub's Spec Kit: write and check the spec before any code, trace every task back to it, and count work as done only when it's proven against it. It doesn't use those tools. It's a lighter version shaped for small apps and AI builders.

What it adds for AI builders: every card is written so a cheap model can build it without guessing, the build is checked harder where data can be lost or leaked (zones), every card is test-first, and an independent review checks the spec before anything is built.
